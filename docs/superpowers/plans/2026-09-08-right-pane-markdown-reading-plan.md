# Чтение Markdown в правой панели: план

**Статус:** реализация выполняется. Широкая валидация ещё ожидается.

Связанная спецификация: [спецификация](../specs/2026-09-08-right-pane-markdown-reading-design.md).

## Базовые условия

Работа ведётся от линии `623986491` с учётом `09a25b1de`, который закрепляет двухъячеечный левый отступ содержимого правой рейки. Область изменения ограничена клиентским TUI. Общий server и stable не трогаются. Новый протокол и внешние зависимости не допускаются. Всё добавленное состояние сессионно.

## Этап 1. Базовое состояние и навигация

1. Ввести сессионную модель открытых документов, активной страницы и выбранного режима страницы.
2. Сохранить единое пространство правой области с достижимыми Diff, Files и Documents даже при открытом документе.
3. Поддержать несколько одновременно открытых страниц, включая spec и plan.
4. Задать режимы Read, Source и Changes. Для нового документа выбрать Read.
5. При refresh сохранять ручной выбор страницы и режима, если он действителен. При недействительном выборе применять безопасный fallback к существующей странице в Read.

## Этап 2. Рендереры и открытие из Files

1. Реализовать представления Read, Source и Changes в Documents.
2. Для отсутствующего совпадающего diff в Changes показывать «изменений нет», а при недоступном snapshot рабочей области показывать загрузку. Ошибки открытия остаются в существующих безопасных notices, а позднее чтение linked file сохраняет последний хороший snapshot без нового поля ошибки страницы.
3. Связать выбор `.md` в Files с открытием либо активацией соответствующего документа. Не менять поведение файлов других типов.
4. Применить двухъячеечный левый отступ `09a25b1de` к геометрии рендеринга, hit testing и копирования.
5. Сохранить ограниченный кэш Markdown, ключуемый страницей, сигнатурой содержимого, шириной и параметрами рендера. Source и Changes вычислять из текущей страницы, snapshot и режимного UI-состояния, не заявляя отдельные поля сессии или режима в каждом ключе.
6. Не выполнять HTML, скрипты, команды, сетевые загрузки или небезопасные переходы по пути.

## Этап 3. Независимый обзор и коррекция

1. Сверить реализацию с A1-A15 из [спецификацией](../specs/2026-09-08-right-pane-markdown-reading-design.md).
2. Отдельно проверить достижимость Diff и Files при открытых Documents, изоляцию сессионного состояния и сохранение ручного выбора после refresh.
3. Проверить отсутствие изменений shared server, stable, протокола и внешних зависимостей.
4. Исправить найденные расхождения до запуска широкого набора.

## Этап 4. Последовательные тесты

1. Сначала запустить фокусированные тесты состояния, навигации, открытия `.md`, режимов, no-diff, ошибок, кэша, копирования и hit testing.
2. После успешных фокусированных тестов запустить широкий набор TUI-тестов. Этот этап выполняется последовательно, чтобы не смешивать результаты общего таргета.
3. Зафиксировать, что широкая валидация пока ожидается, если её не удалось завершить в текущем цикле.

## Этап 5. Изолированная runtime-приёмка socket

1. В изолированном socket runtime проверить реальную навигацию между Diff, Files и Documents.
2. Проверить одновременное открытие spec и plan, Read по умолчанию, ручную смену Source и Changes и сохранение выбора при refresh.
3. Проверить открытие `.md` из Files, двухъячеечную геометрию, no-diff, локальные ошибки, копирование и безопасное отсутствие внешнего исполнения.
4. Сопоставить наблюдения с A1-A15 и только затем считать широкую валидацию завершённой.

## Результат

После завершения этапов контракт спецификации считается реализованным без изменения shared server/stable, протокола или внешних зависимостей. На момент составления плана реализация находится в процессе, а широкая валидация ещё не выполнена.
